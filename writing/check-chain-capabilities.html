Check what a chain exposes before you trust an XCM route

Tyler Woods · 2026

A chain can accept a WebSocket connection, answer a balance query, and still have no way to build the transfer you asked for. The failure surfaces at build or encode time, after the amount and the recipient are set, and the message names a method rather than the missing capability.

Four transfer methods and two runtime APIs decide whether a route can be built, fee-estimated and dry run. One command prints them, with a live probe next to the flag the SDK actually uses.

The four transfer methods

The XCM SDK can call four extrinsics on PolkadotXcm or XcmPallet. Each covers a different route shape.

  • transfer_assets_using_type_and_then. Required for a relay asset on an origin that does not reserve it, and reached by some external-asset routes. When it is missing, those routes throw TypeAndThenUnavailableError instead of building an invalid call.
  • limited_reserve_transfer_assets and reserve_transfer_assets. The reserve-transfer paths for foreign assets. The limited form carries a weight limit and is the one the SDK prefers.
  • limited_teleport_assets. Teleports, used for trusted-chain routes where the asset is native on both sides.

The two runtime APIs

  • DryRunApi. How the SDK turns a built call into a fee and a success check. Without it, fee estimation falls back to other sources, and the type-and-then path loses the pass that would have replaced its fee placeholder. The public report on that path is xcm-tools#2353.
  • XcmPaymentApi. The fee-query interface the SDK prefers when it exists. Without it, the SDK uses paymentInfo or dry run instead, and some execution paths check the flag before trusting a fee from this source.

Run it

The script is check-chain-capabilities.mjs. It uses @paraspell/sdk from npm and connects to each chain's default endpoint.

npm install @paraspell/sdk
node check-chain-capabilities.mjs Hydration Peaq Heima BifrostPolkadot

How to read it

  • Method no. The SDK falls back to another transfer path, or throws for routes that need the missing method. It does not build the call.
  • Runtime API no. Fee estimation and dry run fall back. For type-and-then, a missing DryRunApi is the path behind the placeholder report above.
  • Live and registry disagree. The SDK follows the registry, not the live probe. If a chain enabled a runtime API after the asset map was generated, the SDK still takes the fallback. Update @paraspell/assets or pass a custom chain with the correct flag.
  • A question mark. The probe hit an error it could not classify, usually a transient connection failure. Run it again.
  • Everything missing. Check the endpoint. The probe reads the metadata the SDK would use, and a provider stuck at an old block serves an old metadata set. That is a provider problem, not a chain problem.

What it does not check

Asset listings, decimals, existential deposits, the destination's support for the asset, the reserve chain, XCM version negotiation, and whether a route exists at all. Those come from the asset map and the destination, not from the origin's metadata. A green table is a necessary condition, not a route test.
